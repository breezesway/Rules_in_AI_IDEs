# 实际开发记录

## PDF合并功能开发总结

### 技术架构决策
- **文件选择方式变更**：从拖拽上传改为 Electron 原生对话框
  - **原因**：浏览器环境中 File 对象缺少 path 属性，无法获取真实文件路径
  - **解决方案**：使用 `dialog.showOpenDialog` 获取文件路径数组
- **状态管理简化**：使用 React 内置 useState 而非第三方状态管理
  - **原因**：功能相对简单，不需要复杂的状态管理
- **通知系统选择**：最终采用 React Toast 而非系统通知
  - **原因**：系统通知在某些环境下不稳定，Toast 更可靠且样式统一

### 关键技术实现
- **IPC 通信模式**：
  - 主进程：处理文件操作、PDF合并、进度报告
  - 渲染进程：UI交互、状态管理、进度显示
- **文件处理流程**：
  1. 文件选择 → 2. 文件验证 → 3. PDF合并 → 4. 保存文件 → 5. 结果通知
- **错误处理策略**：
  - 文件级别错误：单个文件处理失败时继续处理其他文件
  - 系统级别错误：整个操作失败时显示友好错误信息
  - 用户操作错误：文件覆盖确认、取消操作支持

### UI/UX 优化
- **模态框布局**：采用固定头部/底部，可滚动中间内容的布局
- **进度反馈**：实时显示当前处理文件和整体进度
- **视觉一致性**：所有组件遵循统一的设计系统（圆角、间距、颜色）

### 性能考虑
- **内存管理**：大文件处理时的内存优化
- **进度报告**：避免过于频繁的进度更新影响性能
- **文件验证**：在合并前验证文件有效性，避免处理过程中失败

## 图片压缩功能开发总结

### 技术架构决策
- **原生模块集成挑战**：Sharp 库在 Electron 环境中的加载问题
  - **问题**：Sharp 是原生模块，Vite 打包时无法正确处理动态加载
  - **解决方案**：配置 Vite 外部依赖 + 动态导入 `await import('sharp')`
- **文件选择方式统一**：沿用 PDF 合并的成功经验
  - **原因**：Electron 原生对话框比浏览器文件选择更可靠
  - **实现**：`dialog.showOpenDialog` 支持图片格式过滤
- **压缩算法优化**：从简单质量压缩到智能迭代压缩
  - **按质量等级压缩**：用户最常用的压缩方式，支持10%-100%质量调节
  - **按文件大小压缩**：智能迭代算法，精确逼近目标文件大小
  - **按图片尺寸压缩**：保持原始比例的尺寸调整

### 关键技术实现
- **Sharp 动态加载**：
  ```typescript
  const sharp = await import('sharp');
  const sharpInstance = sharp.default(filePath);
  ```
- **Vite 配置优化**：
  ```typescript
  // vite.main.config.ts
  export default defineConfig({
    build: {
      rollupOptions: {
        external: ['sharp']
      }
    }
  });
  ```
- **智能按文件大小压缩算法**：
  - **格式特性优化**：针对JPEG、PNG、WebP不同格式的压缩特性调整初始质量估算
  - **迭代逼近算法**：最多5次迭代，10%容差范围内精确控制文件大小
  - **质量自适应调整**：根据实际压缩效果动态调整质量参数
  - **临时文件管理**：使用临时文件测试压缩效果，自动清理
- **多格式支持**：JPEG、PNG、WebP 的质量压缩适配
- **文件处理流程**：
  1. 文件选择 → 2. 格式检测 → 3. 智能压缩 → 4. 格式转换 → 5. 保存文件

### 压缩功能特性
- **按质量等级压缩**：10%-100% 可调节质量滑块，高质量时智能防止文件变大
- **按文件大小压缩**：精确控制输出文件大小，智能迭代逼近目标大小
- **按图片尺寸压缩**：调整图片宽度和高度，保持原始比例
- **格式转换支持**：保持原格式或转换为 JPG/PNG/WebP，针对不同格式优化压缩参数
- **文件名后缀自定义**：默认添加 "_compressed" 后缀
- **重名文件处理**：集成应用配置，支持自动编号或询问覆盖
- **批量处理**：支持多文件同时压缩
- **错误容错**：单文件失败不影响其他文件处理

## 按文件大小压缩功能深度优化（2024-12-29）

### 优化目标
- **精确控制**：将输出文件大小控制在目标大小的±10%范围内
- **格式适配**：针对JPEG、PNG、WebP不同格式的压缩特性优化算法
- **性能平衡**：在压缩精度和处理速度之间找到最佳平衡点

### 算法设计
- **智能初始估算**：
  - JPEG格式：压缩效率高，使用 `compressionRatio * 120` 估算
  - PNG格式：压缩效率较低，使用 `compressionRatio * 100` 估算  
  - WebP格式：压缩效率最高，使用 `compressionRatio * 130` 估算
- **迭代优化策略**：
  - 最多5次迭代，避免过度处理
  - 10%容差范围，平衡精度和性能
  - 动态质量调整，根据实际效果智能修正
- **临时文件管理**：
  - 使用临时文件测试压缩效果
  - 自动清理临时文件，避免磁盘空间浪费
  - 达到目标时直接重命名，提高效率

### 技术实现细节
```typescript
// 格式特性优化的质量估算
if (outputFormat === 'jpeg' || outputFormat === 'jpg') {
  estimatedQuality = Math.max(20, Math.min(85, Math.round(compressionRatio * 120)));
} else if (outputFormat === 'png') {
  estimatedQuality = Math.max(10, Math.min(80, Math.round(compressionRatio * 100)));
} else if (outputFormat === 'webp') {
  estimatedQuality = Math.max(25, Math.min(90, Math.round(compressionRatio * 130)));
}

// 迭代优化逻辑

  }
```

### 性能优化
- **早期终止**：达到目标大小时立即停止迭代
- **收敛检测**：连续两次压缩结果相近时停止迭代
- **资源清理**：及时清理临时文件，避免资源泄漏

### 图片压缩质量问题修复（2024-12-29）
- **问题描述**：选择高质量等级压缩时，生成的图片文件比原图更大
- **根本原因**：
  1. PNG格式错误使用了`quality`参数（PNG不支持此参数）
  2. 缺少按文件大小压缩的实现逻辑
  3. 高质量压缩时未检查输出文件大小
- **修复方案**：
  1. **PNG格式优化**：改用`compressionLevel`参数，添加`progressive: true`
  2. **智能质量控制**：高质量设置时先保存临时文件检查大小，如果变大则自动降低质量
  3. **完整压缩方式**：实现按文件大小压缩，根据目标大小智能估算质量级别
  4. **尺寸压缩增强**：为按尺寸压缩添加适中的质量设置
- **技术细节**：
  - 使用临时文件机制检查压缩效果
  - 不同格式使用正确的压缩参数（JPEG用quality，PNG用compressionLevel，WebP用quality）
  - 添加文件大小保护机制，确保压缩后文件不会意外变大

### 保存位置设置不生效问题修复（2024-12-29）
- **问题描述**：在应用设置中修改默认保存位置后，工具中实际保存位置未更新
- **根本原因**：
  1. 工具组件的useEffect依赖条件错误：`if (isOpen && !saveLocation)`
  2. 保存位置作为依赖项，一旦设置后就不会再触发更新
  3. 组件缓存了第一次获取的保存位置，不响应配置变化
- **修复方案**：
  1. **修改初始化逻辑**：每次打开工具时都重新获取最新配置
  2. **移除错误依赖**：从useEffect依赖数组中移除`saveLocation`
  3. **配置清理机制**：如果用户清空了默认保存位置，工具也相应清空缓存
- **技术细节**：
  ```typescript
  // 修复前（有问题）
  React.useEffect(() => {
    if (isOpen && !saveLocation) { // ❌ 条件错误
      // 获取配置...
    }
  }, [isOpen, saveLocation]); // ❌ 依赖项问题

  // 修复后（正确）
  React.useEffect(() => {
    if (isOpen) { // ✅ 每次打开都获取
      // 获取配置并清理旧设置...
    }
  }, [isOpen]); // ✅ 只依赖isOpen
  ```
- **影响范围**：图片压缩工具和PDF合并工具都进行了相同修复
- **用户体验改进**：设置修改后立即生效，无需重启应用

### 交互体验统一优化（2024-12-29）
- **问题描述**：PDF合并和图片压缩两个工具的操作完成后交互行为不一致
  - PDF合并：成功后只重置表单，弹框保持打开状态
  - 图片压缩：成功后自动关闭弹框
- **优化目标**：统一两个工具的交互体验，提供一致的用户操作流程
- **修复方案**：
  - 修改PDF合并组件的成功处理逻辑
  - 移除文件状态更新和延迟重置的复杂逻辑
  - 成功后立即重置表单并关闭弹框，与图片压缩保持一致
- **技术实现**：
  ```typescript
  // 修复前：复杂的状态管理
  if (result?.success) {
    setFiles(prev => prev.map(f => 
      f.status === 'ready' ? { ...f, status: 'done' as const } : f
    ));
    setProgress(100);
    toast.success('PDF合并完成！');
    setTimeout(() => {
      resetForm();
    }, 500);
  }

  // 修复后：简洁统一的处理
  if (result?.success) {
    toast.success('PDF合并完成！');
    resetForm();
    onClose(); // 自动关闭弹框
  }
  ```
- **用户体验改进**：
  - 操作完成后自动返回主界面，减少用户操作步骤
  - 两个工具的操作流程完全一致，降低学习成本
  - 简化界面状态管理，提高应用响应速度

# 核心设计模式总结

## 应用级别配置管理模式
- **设计原则**：核心设置统一管理，避免重复配置
- **实现方式**：
  - 配置集中存储在应用数据目录
  - 工具组件启动时自动获取应用配置
  - 设置界面集中管理，工具界面只显示状态
- **适用场景**：保存位置、文件处理规则等通用设置
- **优势**：减少用户操作步骤，提供一致的体验

## 通用UI组件复用模式
- **设计原则**：可复用的UI组件放在 `src/ui/` 目录
- **实现方式**：
  - 组件设计时考虑通用性和可配置性
  - 通过 props 控制组件行为和样式
  - 在多个场景中复用同一组件
- **典型案例**：SaveLocationSelector 组件
- **优势**：保证界面一致性，减少重复代码

## 渐进式功能简化模式
- **设计原则**：从复杂功能开始，逐步简化到最佳体验
- **实现过程**：
  1. 初期：每个工具独立配置保存位置
  2. 中期：提取通用组件，保持功能完整
  3. 后期：移除工具级别配置，统一到应用级别
- **决策依据**：用户反馈、使用频率、维护成本
- **优势**：持续优化用户体验，降低系统复杂度
